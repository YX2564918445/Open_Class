## 准双向口：为什么读引脚前必须先写 1

这是 51 单片机最经典、也最容易考倒初学者的问题。本讲代码里有一行专门为此而写，所以必须先讲清楚。

51 单片机的 I/O 口内部结构（简化版）是这样的：

```text
              VCC
               │
        ┌──────┴──────┐
        │  内部弱上拉  │   （P1/P2/P3 有，P0 没有）
        │   ~50kΩ     │
        └──────┬──────┘
               │
  写 1 ────┐   │
           ├──┤ 锁存器 ├──┬──── 引脚
  写 0 ────┘   │         │
               │      ┌──┴──┐
               │      │ MOS │
               │      └──┬──┘
               │         │
               │        GND
```

- **写 1 时**：场效应管**截止**（断开），引脚和 GND 之间断路，此时引脚电平**由外部电路决定**——外部接了按键，就能读到外界的高低电平。
- **写 0 时**：场效应管**导通**，引脚被**强行拉到 GND**，不管外面接什么，读回来永远是 0。

读引脚时读的是外部电路实际呈现的电平，而不是锁存器里的值。所以：

> 如果上一次你写了 `0`，MOS 管还处于导通状态，引脚被钳在低电平，此时你去读，**永远读到 0**，按键按不按都一样。

因此**读引脚之前必须先写 1**，让 MOS 管截止，把引脚"解放"出来交给外部电路。这种做法叫**准双向口**——它既能做输出也能做输入，但做输入前需要人工"配置"一下。

> ⚠ **P0 口是例外**：P0 内部没有上拉电阻（开漏输出），如果要用 P0 接按键，必须外接 10 kΩ 上拉电阻到 VCC，否则读出来的是乱码。本讲用的是 P3，内部有弱上拉，可以直接接按键。

## 按键电路

普中 A2 的 4 个独立按键，一端接单片机引脚，另一端接 GND：

```text
      P3.0 ~ P3.3（单片机引脚）
            │
            │
      内部弱上拉 ~50kΩ 到 VCC
            │
          ┌─┴─┐
          │   │  按键 K1 ~ K4
          └─┬─┘
            │
           GND
```

| 按键状态 | 引脚电平 | 代码读到 | `if(KEY1 == 0)` |
| --- | --- | --- | --- |
| 松开 | 被内部弱上拉拉到 5 V | 1 | 不成立 |
| 按下 | 直接连到 GND，被拉成 0 V | 0 | 成立 |

所以 `if(KEY1 == 0)` 的含义是"按键被按下了"。

**为什么四个按键的引脚是 P3.1、P3.0、P3.2、P3.3，而不是整齐的 P3.0~P3.3？**

```c
sbit KEY1 = P3^1;
sbit KEY2 = P3^0;
sbit KEY3 = P3^2;
sbit KEY4 = P3^3;
```

这是**普中 A2 的 PCB 布线决定的**，代码只是如实反映了硬件实际连线——K1 接在 P3.1，K2 接在 P3.0。

> ⚠ 不要假设引脚编号一定连续，永远以原理图/开发手册为准。另外再说一次：P3.2 与红外接收头共用，做本实验前记得拔掉红外跳线帽。

## 按键抖动：为什么必须消抖

理想的按键波形是干净的方波，但实际上机械触点在闭合/断开瞬间会**弹跳多次**：

```text
理想情况：
────────┐                    ┌────────
        │                    │
        └────────────────────┘
        按下                 松开

实际情况（机械触点抖动）：
────────┐ ┌┐ ┌─┐ ┌┐ ┌───────┐ ┌┐ ┌─┐ ┌───
        │ ││ │ │ ││ │       │ ││ │ │ │
        └─┘└─┘ └─┘└─┘       └─┘└─┘ └─┘
        ↑                     ↑
     按下瞬间弹跳          松开瞬间弹跳
     （持续 5 ~ 20 ms）     （持续 5 ~ 20 ms）
```

**如果不处理会怎样？** 单片机扫描速度极快（微秒级），在一次抖动期间可能扫描到几十次"按下"。如果代码是 `if(KEY1 == 0) LED1 = ~LED1;`，LED1 会在一瞬间被反复取反几十次——结果看起来要么没反应，要么随机亮灭，完全不可控。

**软件消抖的思路**：第一次检测到低电平先别信 → 延时 10 ms 等抖动平息 → 再读一次，还是低电平才确认。

这个"**延时 + 二次确认**"结构就是本讲代码的核心。

## 完整代码

文件：[51_Project/3Key_LED/main.c](../51_Project/3Key_LED/main.c)

```c
/*
 * 调用头文件
 */
#include "reg52.h"
#include <intrins.h>    // 提供 _nop_() 函数

/*
 * 引脚定义
 */
// LED1 -- LED4
sbit LED1 = P2^0;
sbit LED2 = P2^1;
sbit LED3 = P2^2;
sbit LED4 = P2^3;
// KEY1 -- KEY4
sbit KEY1 = P3^1;
sbit KEY2 = P3^0;
sbit KEY3 = P3^2;
sbit KEY4 = P3^3;

/*
 * 函数声明
 */
void Delay_ms(unsigned int ms);
void KEY_Scanf(void);

/**
 * @brief  主函数
 * @param  无
 * @retval 无
 */
int main(void)
{
    while(1)
    {
        KEY_Scanf();    // 按键扫描及处理
    }
}

/**
 * @brief  延时函数：产生一段时间的延时效果
 * @param  ms 想要产生延时的毫秒数
 * @retval 无
 */
void Delay_ms(unsigned int ms)
{
    unsigned int i, j;
    for(i = ms; i > 0; i--)
    {
        // 11.0592MHz 晶振，921 个机器周期约为 1ms
        for(j = 110; j > 0; j--)
        {
            _nop_();    // 空操作，消耗 1 个机器周期
        }
    }
}

/**
 * @brief  按键扫描及逻辑处理
 * @param  无
 * @retval 无
 */
void KEY_Scanf(void)
{
    // 51 单片机读取引脚电平值，最好是先将对应引脚设置为高电平
    KEY1 = 1;
    KEY2 = 1;
    KEY3 = 1;
    KEY4 = 1;

    // KEY1
    if(KEY1 == 0)
    {
        Delay_ms(10);   // 消抖
        if(KEY1 == 0)
        {
            LED1 = ~LED1;   // LED1 状态取反
        }
        while(KEY1 == 0);   // 等待按键释放
    }
    // KEY2
    else if(KEY2 == 0)
    {
        Delay_ms(10);   // 消抖
        if(KEY2 == 0)
        {
            LED2 = ~LED2;   // LED2 状态取反
        }
        while(KEY2 == 0);   // 等待按键释放
    }
    // KEY3
    else if(KEY3 == 0)
    {
        Delay_ms(10);   // 消抖
        if(KEY3 == 0)
        {
            LED3 = ~LED3;   // LED3 状态取反
        }
        while(KEY3 == 0);   // 等待按键释放
    }
    // KEY4
    else if(KEY4 == 0)
    {
        Delay_ms(10);   // 消抖
        if(KEY4 == 0)
        {
            LED4 = ~LED4;   // LED4 状态取反
        }
        while(KEY4 == 0);   // 等待按键释放
    }
}
```

## 逐句讲解

### 头文件（第 1 ~ 3 行）

```c
/*
 * 调用头文件
 */
#include "reg52.h"
#include <intrins.h>    // 提供 _nop_() 函数
```

- `/* ... */` 是 C 语言的**块注释**，编译器会完全忽略。
- `#include` 是**预处理指令**，效果是"把那个文件的内容原样复制到这个位置"。预处理发生在编译之前。
- `"reg52.h"` 用**双引号**：编译器**先**在当前工程目录找，找不到再去系统目录找。
- `<intrins.h>` 用**尖括号**：编译器**只**去系统目录（Keil 安装目录下的 `C51\INC\`）找。

习惯上：**自己写的头文件用双引号，编译器自带的用尖括号。**

| 头文件 | 提供什么 | 本工程用到的 |
| --- | --- | --- |
| `reg52.h` | 端口的 `sfr` 定义（`P0`/`P1`/`P2`/`P3`…） | 需要 `P2`、`P3` 这两个名字 |
| `intrins.h` | 内部函数（`_nop_`、`_crol_`…） | 需要 `_nop_()` |

> ⚠ 删掉 `#include "reg52.h"` 会报错 `undefined identifier P2`；删掉 `#include <intrins.h>` 会报错 `undefined identifier _nop_`。

### 引脚定义（第 5 ~ 15 行）

```c
/*
 * 引脚定义
 */
// LED1 -- LED4
sbit LED1 = P2^0;
sbit LED2 = P2^1;
sbit LED3 = P2^2;
sbit LED4 = P2^3;
// KEY1 -- KEY4
sbit KEY1 = P3^1;
sbit KEY2 = P3^0;
sbit KEY3 = P3^2;
sbit KEY4 = P3^3;
```

这一段是**软件与硬件的"对接表"**。`sfr` / `sbit` 的语法和 `^` 的特殊含义已在[第 2 讲](02_流水灯.md#sfr-与-sbit端口怎么变成代码里的名字)讲过，这里补充几点实践意义：

**① 为什么叫 `LED1` 而不是直接写 `P2^0`？**

因为可读性和可维护性。下面两段代码功能完全相同：

```c
LED1 = ~LED1;    /* 一眼看出：翻转 LED1 */

P2^0 = ~P2^0;    /* 得在脑子里翻译一次：哦，这是 LED1 */
```

更重要的是：如果哪天板子换了，LED1 从 P2.0 挪到了 P1.5，你只需要改这一行 `sbit` 定义，所有用到 `LED1` 的代码都不用动。这是嵌入式编程里最基础的"硬件抽象"思想。

**② 位号对应关系**

| LED | 引脚 | KEY | 引脚 |
| --- | --- | --- | --- |
| LED1 | P2.0 | KEY1 | P3.1 |
| LED2 | P2.1 | KEY2 | P3.0 |
| LED3 | P2.2 | KEY3 | P3.2 |
| LED4 | P2.3 | KEY4 | P3.3 |

LED 这组是连续的 P2.0 ~ P2.3，按键那组是错位的（原因见[按键电路](#按键电路)）。

**③ 为什么只定义了 4 个 LED？**

因为本工程只用到 4 个。普中 A2 上虽然接了 8 个 LED（P2.0 ~ P2.7），没用上的位就不需要定义。

**④ 上电初始状态是什么？**

单片机复位后，P0、P1、P2、P3 全部等于 `0xFF`，也就是 8 个引脚全是高电平。对应到共阳 LED 电路上，就是**上电后 4 个 LED 全灭**。

代码里没有任何一行初始化 LED 状态，这不是疏漏，而是利用了硬件的复位默认值。如果想强制上电全亮，可以显式写 `P2 = 0x00;`。

### 函数声明（第 17 ~ 19 行）

```c
/*
 * 函数声明
 */
void Delay_ms(unsigned int ms);
void KEY_Scanf(void);
```

这两行叫**函数原型声明**。它告诉编译器："后面会有一个叫 `Delay_ms` 的函数，接受一个 `unsigned int` 参数，没有返回值。"

**为什么必须写？** 因为 C 语言是**从上往下**编译的。`main` 在第 26 行，而 `Delay_ms` 的定义在第 40 行、`KEY_Scanf` 在第 59 行——都排在 `main` 后面。编译到 `main` 里的 `KEY_Scanf();` 时，编译器还没见过它，不知道这个函数长什么样、参数对不对。函数声明就是提前"备案"。

如果没声明，Keil C51 会给出警告 `warning C206: 'KEY_Scanf': missing function-prototype`，并假定它返回 `int`。对于这个工程可能还能跑，但这是很危险的习惯——一旦参数类型不匹配（传了浮点数、传了指针），就会产生难以排查的 bug。

**写法要点**：

- `void KEY_Scanf(void);` —— 参数列表写 `(void)` 表示"明确不接受任何参数"。如果写空括号 `()`，在 C51 里表示"参数不明确"，含义不同。
- 函数定义如果写在 `main` 之前，声明就可以省略。本工程把 `main` 放最前面、把实现放后面，这是嵌入式代码里常见的组织方式——让读者一打开文件就能看到程序主干。

### 主函数 main（第 21 ~ 32 行）

```c
/**
 * @brief  主函数
 * @param  无
 * @retval 无
 */
int main(void)
{
    while(1)
    {
        KEY_Scanf();    // 按键扫描及处理
    }
}
```

**① 注释块**

`/**` 开头（比普通 `/*` 多一个星号）表示这是一段 **Doxygen 风格**的结构化文档注释。Keil 和很多 IDE 能识别 `@brief`（简介）、`@param`（参数）、`@retval`（返回值）这些标签，自动生成函数说明文档。养成这个习惯很好。

**② `int main(void)`**

`main` 是 C 程序的唯一入口。单片机复位后总是从 `main` 的第一行开始执行。`(void)` 表示不接受参数。

本工程 `main` 里没有任何 `return` 语句——这是合法的，因为 `while(1)` 是个死循环，程序永远走不到函数结尾。

**③ `while(1)` —— 单片机的灵魂**

`while(1)` 的条件永远为真，所以这是一个**死循环**。

> ⚠ **单片机程序必须是一个死循环**，这一点和 PC 程序完全不同，必须理解清楚：
>
> - PC 上程序执行完 `main` 就退出，把控制权交还操作系统；
> - 单片机**没有操作系统**。如果 `main` 执行完返回了，CPU 会跑到程序存储器里未定义的地方去执行垃圾数据，行为完全不可预测（可能进入死循环、可能触发看门狗复位、可能乱操作寄存器把外设搞坏）。
>
> 所以单片机程序的标准结构永远是：**上电 → 初始化 → `while(1) { 干活 }`**。

主循环里只有一件事：不断调用 `KEY_Scanf()`，也就是不停扫描按键有没有被按下。扫描一次的时间是微秒级的，所以人按下去的那一瞬间就会被捕捉到。

```text
      复位
       │
       ▼
   ┌─────────┐
   │  main   │
   └────┬────┘
        │ 进入 while(1)
        ▼
   ┌──────────────────┐
   │   KEY_Scanf()    │◄─────┐
   │   扫描 4 个按键   │      │
   │   有按下就处理    │      │
   └────────┬─────────┘      │
            │                │
            └────────────────┘
           永不退出，反复扫描
```

### Delay_ms

```c

{

    for(i = ms; i > 0; i--)
    {
        // 11.0592MHz 晶振，921 个机器周期约为 1ms

        {

```

这段代码和[第 2 讲](02_流水灯.md#delay_ms-的真相)的 `Delay_ms` **一字不差**，逐句分析（包括"注释说 1 ms、实际约 0.6 ~ 1.0 ms"的核对、定时器方案、Keil 仿真标定方法）请回看第 2 讲，这里不再重复。

本讲只需要关心一点：**`Delay_ms(10)` 在这里用于消抖**。只要它大于按键抖动时间（通常 5 ~ 20 ms 中的较大部分），消抖就是有效的；它到底精确是 10 ms 还是 7 ms，对功能没有影响。

### KEY_Scanf（逐句讲解）

函数名 `KEY_Scanf`（`Scanf` 这里其实是 "Scan" 的意思，作者写法上不太规范，函数名最好写成 `KEY_Scan`）表示"按键扫描及逻辑处理"。它既负责检测按键，也负责执行动作。

#### 第 ① 段：预置高电平

```c
// 51 单片机读取引脚电平值，最好是先将对应引脚设置为高电平
KEY1 = 1;
KEY2 = 1;
KEY3 = 1;
KEY4 = 1;
```

这就是[准双向口](#准双向口为什么读引脚前必须先写-1)讲的特性。`KEY1 = 1;` 等价于 `P3.1 = 1;`，效果是：

1. P3 口第 1 位的**输出锁存器**被置 1；
2. 内部场效应管**截止**，引脚不再被强行拉低；
3. 引脚电平交给**外部电路**决定（松开时被内部弱上拉成高电平，按下时被按键拉到 GND）。

**这四行每扫描一次就要执行一次，是不是浪费？**

理论上，只要 P3 口的锁存器从来没被写过 0，读之前就永远是 1，这几行可以只在初始化时写一次。但作者放在 `KEY_Scanf` 里每次都写，是出于**稳健性**考虑——这是"防御性编程"：不管之前有没有谁把 P3 的某一位改过（比如以后扩展代码时不小心写了 `P3 = 0x00`），这里每次都重新置 1，保证读引脚的行为一定正确。

代价很小：4 条位操作指令，一共也就几个机器周期，相对于后面 `Delay_ms(10)` 的几万机器周期完全可以忽略。

> **注意**：这四行是在**函数开头无条件执行**的，而不是在 `if` 里。因为它们必须在**读之前**执行，而不是在"确认按下之后"。

#### 第 ② 段：key1 的处理

```c
// KEY1
if(KEY1 == 0)
{
    Delay_ms(10);   // 消抖
    if(KEY1 == 0)
    {
        LED1 = ~LED1;   // LED1 状态取反
    }
    while(KEY1 == 0);   // 等待按键释放
}
```

> ⚠ **`==` 和 `=` 的区别**——这是 C 语言最经典的错误：
>
> | 写法 | 含义 |
> | --- | --- |
> | `KEY1 == 0` | **比较**：KEY1 是否等于 0？结果是"真"或"假" |
> | `KEY1 = 0` | **赋值**：把 KEY1 设成 0 |
>
> 如果手滑写成 `if(KEY1 = 0)`，含义就变成了"把 KEY1 赋值为 0，然后判断这个赋值表达式的值（也就是 0）是否为真"，**永远为假，分支永远不执行**，而且会把 P3.1 强行拉低。更糟的是 Keil 可能只给个警告，程序编译通过但行为完全不对。**务必小心。**

**第一层 `if(KEY1 == 0)`：初步检测**

`KEY1` 代表 `P3.1` 引脚的电平。松开时是 1，按下时是 0。所以这个条件的意思是"**KEY1 可能被按下了**"。

为什么说"可能"？因为此刻读到的 0 也可能只是**机械抖动**产生的瞬间电平。

**`Delay_ms(10);` —— 软件消抖**

停顿 10 毫秒左右。抖动通常持续 5 ~ 20 ms，这 10 ms 足够让大多数抖动平息。在延时期间程序什么也不做，就只是"干等"——这正是软件消抖的代价。

**第二层 `if(KEY1 == 0)`：二次确认**

延时之后再读一次。如果**仍然是 0**，说明 10 ms 后按键还稳稳地按着——**不是抖动，是真的按下了**。

这种"延时前后各读一次，两次都满足才确认"的结构，叫做"**二次确认消抖**"。

**`LED1 = ~LED1;` —— 状态取反**

这是最核心的一行。`~` 是**按位取反**运算符（在 `sbit` 定义语句里 `^` 被特殊解释为位选择，但 `~` 这里就是标准的按位取反）。

`LED1` 是一个**位变量**，只有 0 和 1 两种取值。但在 C 语言里，**位变量一旦参与运算，就会先被提升成整数**（和[第 2 讲](02_流水灯.md#逐句讲解)里讲的整数提升是同一回事），所以 `~LED1` 实际是在 16 位的 `int` 上做取反，然后**只保留最低位**赋回给位变量：

| LED1 当前值 | `~LED1`（16 位） | 最低位 | 赋值后 LED1 | LED 硬件效果 |
| --- | --- | --- | --- | --- |
| 0 | 0xFFFF | 1 | 1 | 引脚变高 → 灭 |
| 1 | 0xFFFE | 0 | 0 | 引脚变低 → 亮 |

一句话：`LED1 = ~LED1;` 就是"**翻转**"——灭的变亮，亮的变灭。

> **`LED1 = !LED1;` 行不行？** 也可以。`!` 是**逻辑非**：`!0 = 1`，`!1 = 0`，对位变量来说结果和 `~` 完全一样。区别在于 `~` 是按位取反（对多位数据会有多个位翻转），`!` 是逻辑取反（只看"是不是 0"）。
>
> 但 Keil 对位变量上的 `~` 能直接生成 `CPL` 取反指令，效率最高，所以位操作里通常用 `~`。

**`while(KEY1 == 0);` —— 等待按键释放**

注意行尾那个**分号**——它就是这个 `while` 的循环体（空语句）。含义是：

> 只要 KEY1 还是 0（还按着），就一直在原地打转，什么也不干。直到你松手，KEY1 变成 1，循环结束，函数才继续往下走。

**没有这一行会怎样？** 假设删掉它，那么在主循环里：

- 第 1 次扫描：`KEY1 == 0` → 消抖 → LED1 取反 → 返回
- 第 2 次扫描：KEY1 仍然是 0（你还按着）→ 消抖 → LED1 又取反 → 返回
- 第 3 次扫描：……

由于主循环速度极快，你按住 1 秒钟，LED1 会被翻转成千上万次。最终你松手时看到的亮度取决于松手瞬间的奇偶性——看起来就是莫名其妙地闪烁或随机亮灭。

加上 `while(KEY1 == 0);` 之后，**一次物理按压 = 一次翻转**，行为完全可控。

**这个 while 的三个副作用（要清楚）**：

1. **阻塞**：程序被"卡"在这里，这期间不会去扫描其他按键。你按住 KEY1 的同时去按 KEY2，程序完全不予理会。
2. **占用 CPU**：虽然是空转，但 CPU 一直在满速运行，没法省电。
3. **长按无区别**：按住 1 秒和按住 1 分钟效果完全一样，都是一次翻转。要做"长按"功能，这个结构就不够了。

#### 第 ③④⑤ 段：KEY2 / KEY3 / KEY4

这三段和第 ② 段**结构完全相同**，只是把 `KEY1`/`LED1` 换成了 `KEY2`/`LED2`、`KEY3`/`LED3`、`KEY4`/`LED4`。

唯一需要讲的新知识点：**为什么用 `else if` 而不是 4 个独立的 `if`？**

假设改成 4 个独立 `if`，那么当你**同时按下 KEY1 和 KEY2** 时，第一个 `if` 执行完（并等待 KEY1 释放）之后，如果 KEY2 此时还按着，第二个 `if` 也会执行——**一次操作触发了两个动作**。

而用 `else if` 串起来之后：

```text
KEY1==0 ?
   │ 是 ──► 处理 KEY1 ──► 跳过后面所有 else if
   │ 否
   ▼
KEY2==0 ?
   │ 是 ──► 处理 KEY2 ──► 跳过后面所有 else if
   │ 否
   ▼
KEY3==0 ?
   │ 是 ──► 处理 KEY3 ──► 跳过后面所有 else if
   │ 否
   ▼
KEY4==0 ?
   │ 是 ──► 处理 KEY4
   │ 否
   ▼
（什么也不做，返回）
```

**一次扫描最多只处理一个按键**，逻辑清晰、行为可预测。这就是 `else if` 在这段代码里的意义。

## 运行效果

假设上电后 4 个 LED 全灭（硬件复位默认），你按了一下 KEY1：

| 时刻 | 事件 |
| --- | --- |
| t0 | 上电复位，`P2 = 0xFF`，4 个 LED 全灭 |
| t1 | `main` 进入 `while(1)`，开始反复调用 `KEY_Scanf()` |
| t2 | 你按下 KEY1（P3.1 接 GND） |
| t3 | `KEY1 = 1;` 预置高电平；`KEY1 == 0 ?` → 成立 |
| t4 | `Delay_ms(10)` ← 等约 10 ms，抖动平息 |
| t5 | 再读 KEY1 → 仍然是 0（确实按着） |
| t6 | `LED1 = ~LED1` → 原来是 1，现在变 0 → P2.0 变低 → LED1 点亮 |
| t7 | `while(KEY1 == 0);` ← 卡在这里等你松手 |
| t8 | 你松手 → KEY1 变 1 → 循环结束，函数返回 |
| t9 | `main` 再次调用 `KEY_Scanf()`，继续扫描…… |

再按一次 KEY1：LED1 从 0 变 1，LED1 熄灭。如此循环。

### 相同点与不同点

| 相同点 | 说明 |
| --- | --- |

| 程序结构 | 逻辑拆分为独立函数 | 全部写在 main 里 |

### 三条通用经验

#### 经验一：`Delay_ms` 应该抽成公共模块

两个工程的 `Delay_ms` **完全相同**，却被复制了两份。真实项目里如果再有第三个、第四个工程，就会变成四份。

**正确的做法**是把它放进独立的 `.c` / `.h` 文件：

```c
/* delay.h */
#ifndef __DELAY_H__
#define __DELAY_H__

void Delay_ms(unsigned int ms);

#endif
```

```c
/* delay.c */
#include "reg52.h"
#include <intrins.h>

void Delay_ms(unsigned int ms)
{
    unsigned int i, j;
    for(i = ms; i > 0; i--)
    {
        for(j = 110; j > 0; j--)
        {
            _nop_();
        }
    }
}
```

其他工程只要 `#include "delay.h"` 就能用，**改一处，处处生效**。

`#ifndef` / `#define` / `#endif` 这一套叫**头文件保护**（Include Guard）。作用是防止同一个头文件被重复包含导致重复定义错误。每个 `.h` 文件都应该加。

本教程两个工程都是单文件，规模还小，不抽出来也能接受；但这是必经的成长路径。

#### 经验二：位操作用 `sbit`，整端口操作用 `#define`

这不是硬规定，但实践上很自然：

- 只关心**某一位**（如单个 LED、单个按键）→ 用 `sbit`，可以独立读写，还能用 `~` 取反；
- 要**同时处理 8 位**（如流水灯、数码管段码）→ 用 `#define` 或直接用寄存器名，整体赋值更简洁。

#### 经验三：软件延时都是"阻塞"的

两个工程都用了软件延时，都带来了同样的问题：

| 场景 | 后果 |
| --- | --- |
| `Waterfall_Light` 的 `Delay_ms(500)` | 7 秒一轮，CPU 全程空转，什么其他事都干不了 |
| `Key_LED` 的 `while(KEY==0)` | 按住一个键时，其他键完全失灵 |
| 两者的 `Delay_ms(10)` 消抖 | 每次按键，程序有 10 ms 完全不响应 |

在真实项目里，这是不可接受的。想象一个既要显示流水灯、又要响应按键、又要和上位机通信的设备——用软件延时会导致按键迟钝、通信丢包。

**解法是硬件定时器 + 中断**：让定时器硬件在后台精确计时，时间到了触发中断，CPU 去执行一小段代码然后立刻返回。这样 CPU 在等待期间可以去做别的事，实现"伪并行"。
