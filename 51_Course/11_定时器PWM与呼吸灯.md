# 第 11 讲：定时器做 PWM 与呼吸灯

> **配套例程**：[51_Project/11BreathingLED](../51_Project/11BreathingLED/)
>
> **面向读者**：自动化与信息工程学院学生科学与技术协会大一成员
>
> **硬件平台**：普中 A2 开发板（主控 STC89C52RC，11.0592 MHz 晶振）
>
> **前置要求**：已完成[第 10 讲：定时器 0](10_定时器秒表.md)，会算初值、会写定时器中断；了解[第 6 讲：直流电机](06_直流电机.md)里用 `Delay_10us` 凑出 PWM 波形的做法。

第 6 讲控电机转速时，用的是 `Delay_10us` 一个电平一个电平地凑出 PWM 波形。那套办法能出效果，但代价很大：CPU 全程耗在延时循环里，主循环一个月都轮不到一次。

这一讲换一个思路——**波形交给定时器，CPU 只负责定参数**。

定时器每 100 µs 进来一次，中断里只做一件事：看一眼"现在该亮还是该灭"，然后把引脚拉一下。主循环则慢悠悠地每 10 ms 把占空比改一点点。两个节奏互不影响：改占空比不会打乱波形，波形也不占主循环的时间。

这就是"硬件定时 + 软件 PWM"——比纯软件 PWM 省 CPU，比真正的硬件 PWM 模块（STM32 才有）实现简单。

**本讲功能**：

| 状态 | 现象 |
| --- | --- |
| 上电 | D1（P2.0）由暗逐渐变亮，约 1 秒到最亮，再用 1 秒变回最暗，循环往复 |
| 同时 | D2（P2.1）每 0.5 秒亮灭一次，和 D1 的呼吸互不干扰 |
| 整个过程中 | 主循环只做一件事：每 10 ms 把占空比 ±1 |

## 从第 6 讲的软件 PWM 说起

### 软件 PWM 是怎么做的

第 6 讲的核心思路是：把一个周期切成很多小段，亮的时间占多少，看起来就有多亮。

```c
while(1)
{
    for(i = 0; i < 100; i++)          // 一个 PWM 周期切成 100 份
    {
        if(i < duty)  LED = 0;        // 前 duty 份：亮
        else          LED = 1;        // 剩下的：灭
        Delay_10us(1);                // 每一份 10 µs
    }
    duty++;                           // 调占空比 → 亮度变化
    ...
}
```

一个周期 100 × 10 µs = 1 ms，频率 1000 Hz。占空比 `duty` 从 0 加到 99，亮度就从全暗到全亮。

### 它为什么占 CPU

上面这段代码的 CPU 时间分配是这样的：

```text
一个 PWM 周期 1 ms：

┌── 第 0 份 ──┬── 第 1 份 ──┬── …… ──┬── 第 99 份 ──┐
│ 写引脚 + 延时 │ 写引脚 + 延时 │        │ 写引脚 + 延时 │
└─────────────┴─────────────┴────────┴──────────────┘
     ↑ 这一整个周期里，CPU 一步都不能走开
```

| 问题 | 具体表现 |
| --- | --- |
| CPU 被占满 | 1 ms 里 CPU 全耗在延时上，主循环只剩"改一个 duty 值"这点空 |
| 加不了别的活 | 想在呼吸的同时响应按键、刷新数码管？做不到，一打断波形就乱 |
| 精度靠延时 | `Delay_10us` 抖一点，频率就不稳 |

呼吸灯本身只需要"每隔一会儿改一次占空比"，可这套写法为了维持波形，把 CPU 死死按在延时循环里。

> ⚠ **本质问题：波形是"周期性重复"的活，不该由主循环来背。** 就像每 10 ms 要浇水这件事，应该定个闹钟，而不是自己一直盯着表看。

### 换一个思路

如果有一个东西能每 100 µs 提醒 CPU 一次"该决定亮灭了"，CPU 只要在那一下做个判断、拉一下引脚，剩下 99% 的时间都是空的。

这个东西就是定时器。

## 用定时器产生 PWM

### 节拍：100 微秒

定时器 0 还是老配方：模式 1、16 位、数机器周期。这次要 100 µs：

```text
100 µs ÷ 1.085 µs ≈ 92 （个机器周期）
65536 - 92 = 65444 = 0xFFA4
```

所以：

```c
TH0 = 0xFF;      // 高字节 0xFF
TL0 = 0xA4;      // 低字节 0xA4
```

> ⚠ **每算完初值都要自己核对一遍：`0xFFA4` 是 65444 吗？** `0xFF00` = 65280，`0xA4` = 164，65280 + 164 = 65444 ✓。65536 − 65444 = 92 ✓。心算一遍能省掉九成的"定时不准"问题。

### 占空比：一个 0~99 的计数器

中断里维护一个永远在 0~99 之间循环的计数器 `pwm_cnt`：

```text
每 100 µs 进来一次：

pwm_cnt:  0   1   2  ……  49  50  ……  99   0   1   2  ……
          ├───────────────┼──────────────┤
          │  pwm_cnt < 50 │ pwm_cnt ≥ 50 │
          │    灯 亮       │   灯 灭       │
          └───────────────┴──────────────┘
          ←───── 一个周期 10 ms ─────→
```

代码只有两句：

```c
if(pwm_cnt < duty)  LED_BREATH = 0;   // 计数器小于占空比 → 低电平 → 亮
else                LED_BREATH = 1;   // 否则 → 高电平 → 灭
```

`duty = 0` 时永远走 `else`，灯全灭；`duty = 100` 时永远走 `if`，灯全亮；`duty = 30` 时一个周期里亮 30 份、灭 70 份，亮度约 30%。

> ⚠ **`duty` 必须能取到 100。** 如果 `duty` 最大只到 99，最亮时也还差一份没亮，看不出差别但逻辑上不完整。这里用 `unsigned char` 存，0~100 完全够。

### 为什么是 100 级

100 级 × 100 µs = 10 ms，也就是 PWM 频率 100 Hz。

这一步要同时照顾三件事：

| 要求 | 说明 |
| --- | --- |
| **频率够高，人眼不觉得闪** | 人眼临界闪烁频率大约 50~60 Hz，100 Hz 有余量 |
| **级数够多，呼吸平滑** | 级数太少会看到"台阶"；100 级肉眼基本看不出跳变 |
| **中断别把 CPU 吃光** | 节拍越短 CPU 负担越重，见下一节 |

三者是互相制约的：节拍定得越短，同样 100 级对应的频率越高（更不闪）、但 CPU 越累；节拍放长，CPU 轻松了，频率又掉下来会闪。

## 中断要多短

### 算一笔时间账

100 µs 等于 92 个机器周期。中断函数每次进来要干这些事：

| 动作 | 大约机器周期 |
| --- | --- |
| 硬件保存现场 + 跳转 | 2~4 |
| 重装 `TH0`/`TL0` | 4 |
| `pwm_cnt++`、判断是否到 100 | 8~10 |
| 比较 `pwm_cnt < duty`，写引脚 | 6~8 |
| 恢复现场 + `RETI` | 2~4 |
| **合计** | **约 25~30** |

也就是说，每个 100 µs 里大约有 30 µs 花在中断上，**CPU 占用约 30%**，还剩 70% 给主循环。这个比例可以接受。

> ⚠ **中断函数里绝对不要加 `Delay_ms`。** 一次 1 ms 的延时就是 10 个节拍的时间，中断还没返回，定时器已经溢出了好几次——波形全乱、亮度全错。中断里只能做"几句赋值"级别的操作。

### 50 微秒为什么不行

有人会想：节拍缩短到 50 µs，同样 100 级就是 200 Hz，岂不是更稳？

50 µs 只有 **46 个机器周期**，而中断体本身就要 25~30 个。剩下的余量太小，一旦编译器优化不好、或者加了两个变量，中断体直接撑满整个节拍：

```text
50 µs 节拍（46 个机器周期）：

┌───────────────────────────┐
│  中断体 25~30 周期          │ 剩下 16~21 周期 ← 主循环只能在这里跑
└───────────────────────────┘
     ↑ 如果中断体再长一点，就一点不剩
```

结果就是主循环几乎跑不动：`duty` 加不上去，灯永远停在某个亮度，看起来像"程序卡死了"。

> ⚠ **判断原则：中断体占用的时间不要超过节拍的 50%。** 留一半给别人，这是经验值。按这个标准，92 个周期里用 30 个是合适的，46 个周期里用 30 个就太勉强了。

## 一个定时器，两个节拍

本讲还想让另一颗灯（D2）每 0.5 秒亮灭一次。要不要再开一个定时器？

不用。**同一个定时器可以派生出任意多个"慢节拍"**，只要在快节拍里数够次数：

```text
100 µs × 100 = 10 ms       ← pwm_cnt 数到 100，PWM 的一个完整周期
10 ms × 50   = 500 ms      ← step_cnt 数到 50，D2 翻转一次
```

代码就写在 `pwm_cnt >= 100` 那个分支里：

```c
if(pwm_cnt >= 100)
{
    pwm_cnt = 0;

    step_cnt++;
    if(step_cnt >= 50)
    {
        step_cnt = 0;
        LED_BLINK = !LED_BLINK;     // 每 500ms 翻转
    }
}
```

这一段每 10 ms 才执行一次，比 PWM 那部分"便宜"得多，所以放在里面不会明显增加中断负担。

> ⚠ **注意 `step_cnt` 的加一是放在 `pwm_cnt >= 100` 里面的。** 如果放在外面（每 100 µs 加一次），数到 50 只有 5 ms，D2 会闪得飞快。

## 为什么主循环只改参数

主循环全部内容：

```c
while(1)
{
    Delay_ms(10);

    if(dir == 1) { duty++; if(duty >= 100) dir = 0; }
    else         { duty--; if(duty == 0)   dir = 1; }
}
```

它只做一件事：**每 10 ms 把 `duty` 挪一格**。从 0 挪到 100 要 1 秒，从 100 挪回 0 又要 1 秒，所以一个完整的呼吸周期约 2 秒。

这里有个关键点：**主循环的 `Delay_ms(10)` 只影响"变亮变暗的快慢"，完全不影响 PWM 的周期和占空比**。因为波形是定时器产生的，你把 `Delay_ms` 改成 50，呼吸变慢，但灯绝不闪。

这就是硬件定时 + 软件 PWM 最值钱的地方：**改参数和产生波形彻底解耦**。

> ⚠ **如果哪天你在主循环里加了很长的延时，看到的现象是"呼吸变慢"，而不是"灯闪"。** 如果看到灯闪，那是频率不够（初值算错）或者定时器被停了，和主循环无关。

## 完整代码

`main.c` 全文如下：

```c
/* 调用头文件 */
#include "reg52.h"
#include "Delay.h"

/* 引脚定义 */
// 注意：P2.5 上还挂着蜂鸣器（插上跳线帽才会响），本讲只动 P2.0 和 P2.1，
// 不会踩到蜂鸣器；如果改成 8 颗灯一起呼吸，第 5 颗亮的时候蜂鸣器会跟着叫
sbit LED_BREATH = P2^0;		// 呼吸灯 D1，共阳极，低电平点亮
sbit LED_BLINK  = P2^1;		// 另一颗灯 D2，由同一个定时器每 500ms 翻转一次


/* 变量定义 */
volatile unsigned char pwm_cnt = 0;			// PWM 计数器，0~99 循环
volatile unsigned char duty = 0;			// 占空比 0~100：数值越大，灯越亮
unsigned char step_cnt = 0;					// 数 PWM 周期用的，只在中断里用


/**
  * @brief	定时器0中断服务函数：每 100us 进来一次
  * @param	无
  * @retval	无
  * @note	本函数做两件事：① 产生 PWM 波形；② 顺便数 500ms 让另一颗灯闪。
  			同一个定时器可以同时管好几个"节拍"，这是它比软件延时强的地方
*/
void Timer0_ISR(void) interrupt 1
{
	// 模式1 不会自动重装初值，每次进来都要自己写
	// 100us 的初值：100us / 1.085us ≈ 92 个机器周期，65536 - 92 = 65444 = 0xFFA4
	TH0 = 0xFF;
	TL0 = 0xA4;

	/* 一、用一个 0~99 的计数器循环，产生 PWM 波形 */
	pwm_cnt++;
	if(pwm_cnt >= 100)			// 100 个节拍 × 100us = 10ms，也就是 100Hz
	{
		pwm_cnt = 0;

		// 下面这几句每 10ms 才执行一次，放在这个 if 里面是为了省时间：
		// 中断函数要尽量短，能少做一次就少做一次
		step_cnt++;
		if(step_cnt >= 50)		// 50 × 10ms = 500ms
		{
			step_cnt = 0;
			LED_BLINK = !LED_BLINK;		// 另一颗灯 0.5 秒亮、0.5 秒灭
		}
	}

	if(pwm_cnt < duty)			// 计数器小于占空比 → 输出低电平 → 灯亮
	{
		LED_BREATH = 0;
	}
	else						// 否则输出高电平 → 灯灭
	{
		LED_BREATH = 1;
	}
}


/**
  * @brief	主函数
  * @param	无
  * @retval	无
*/
int main(void)
{
	unsigned char dir = 1;		// 1 = 正在变亮，0 = 正在变暗

	/* 定时器0 初始化：每 100us 中断一次，作为 PWM 的时间基准 */
	TMOD &= 0xF0;		// TMOD 高 4 位是定时器1 的设置，原样保留；低 4 位清零
	TMOD |= 0x01;		// 定时器0 → 模式1（16 位定时器），用内部时钟定时
	TH0 = 0xFF;			// 100us 初值：100us / 1.085us ≈ 92，65536 - 92 = 0xFFA4
	TL0 = 0xA4;
	ET0 = 1;			// 允许定时器0 中断
	EA  = 1;			// 打开总中断
	TR0 = 1;			// 启动定时器0

	while(1)
	{
		// 主循环只负责"改参数"：每 10ms 让占空比变化 1 级。
		// 这里的延时只决定"变亮变暗的快慢"，PWM 的周期和占空比由定时器保证，
		// 所以调节奏完全不会让灯闪 —— 这正是硬件 PWM 比第 6 讲软件 PWM 强的地方
		Delay_ms(10);

		if(dir == 1)				// 正在变亮
		{
			duty++;
			if(duty >= 100)			// 到最亮，转为变暗
			{
				dir = 0;
			}
		}
		else						// 正在变暗
		{
			duty--;
			if(duty == 0)			// 到最暗，转为变亮
			{
				dir = 1;
			}
		}
	}
}
```

## 逐句讲解

### 定时器初始化

和第 10 讲唯一的区别是初值：

| | 第 10 讲 | 第 11 讲 |
| --- | --- | --- |
| 定时时间 | 10 ms | 100 µs |
| 机器周期数 | 9216 | 92 |
| `TH0`/`TL0` | `0xDC` / `0x00` | `0xFF` / `0xA4` |
| 中断用途 | 计时累加 | 产生波形 |

代码结构一模一样：`TMOD` 设模式 → 写初值 → `ET0`、`EA` → `TR0` 启动。

### 中断里的两段逻辑要分清

```c
pwm_cnt++;                          // ① 每 100 µs 都执行
if(pwm_cnt >= 100) { ...step_cnt... }   // ② 每 10 ms 才执行一次

if(pwm_cnt < duty) LED_BREATH = 0;  // ③ 每 100 µs 都执行
else               LED_BREATH = 1;
```

| 段落 | 执行频率 | 作用 |
| --- | --- | --- |
| ①③ | 每 100 µs | 生成 PWM 波形，决定当前的亮灭 |
| ② | 每 10 ms | 派生出 500 ms 的慢节拍 |

②放在①之后、③之前，是因为它要先把 `pwm_cnt` 归零，③再拿新的 `pwm_cnt` 去比较——顺序反了，归零那一拍就会被算错。

### `pwm_cnt` 为什么要加 `volatile`

`pwm_cnt` 在中断里改、在中断里读，主函数根本没碰它，理论上不用加。但加上也没坏处，而且它和 `duty` 放在一起更整齐——`duty` 是**必须**加的（主循环改、中断读）。

> ⚠ **`duty` 忘了加 `volatile` 的现象非常典型：灯亮度完全不动。** 因为编译器认为中断里读到的 `duty` 永远是最初那个 0，于是把整个比较优化成了固定结果。

### 主循环的方向控制

```c
if(dir == 1) { duty++; if(duty >= 100) dir = 0; }
else         { duty--; if(duty == 0)   dir = 1; }
```

`dir` 只在主循环里用，不需要 `volatile`。边界值用 `>=` 和 `==` 都可以，但推荐写 `>=`——万一 `duty` 因为别的原因越界了，`>=` 还能拉回来。

> ⚠ **`duty--` 在 `unsigned char` 上有个坑：`0 - 1` 会变成 `255`。** 这里用 `if(duty == 0) dir = 1;` 在减之前就拦住了，所以不会出问题。如果写成 `duty--; if(duty == 0)`，减到 0 之后下一轮还会再减一次，直接变成 255，灯会突然全亮。

## 实验现象

烧录后，你会看到：

1. **上电**：D1 从完全熄灭开始，逐渐变亮，大约 1 秒到达最亮，然后逐渐变暗，再用 1 秒回到最暗。一个完整呼吸周期约 2 秒。
2. **同时**：D2 稳定地每 0.5 秒亮灭一次，节奏和 D1 的呼吸完全独立。
3. **呼吸过程平滑**：肉眼看不到明显的台阶（100 级分辨率的极限，贴近看可能能看出轻微跳动）。
4. **把 `Delay_ms(10)` 改成 `Delay_ms(50)`**：呼吸变慢到约 10 秒一个周期，但 D1 依然**不会闪**——频率还是 100 Hz。
5. **把初值改错**（比如写成 `0xFE`/`0xA4`，节拍变成约 250 µs）：D1 会明显闪烁，变成 40 Hz 左右，看着难受。

> ⚠ **呼吸到最暗时灯并没有完全灭。** `duty = 0` 那一瞬间确实全灭，但很快 `duty` 就开始上升。如果你想让呼吸"落到全黑再起来"，在 `duty == 0` 时加一句 `Delay_ms(300)` 停一下，效果更像在"喘气"。

## 常见问题

### 1. 灯一直是暗的，完全不呼吸

按顺序查：

1. `duty` 是不是一直停在 0？检查 `dir` 初始值是不是 1、主循环有没有真的进到 `duty++`；
2. `TR0 = 1` 有没有写？没启动定时器，中断永远不来，`duty` 改了也没用；
3. `EA = 1`、`ET0 = 1` 有没有漏；
4. 中断号是不是 `interrupt 1`（定时器 0），别写成 `interrupt 0`。

### 2. 灯一直全亮

八成是比较方向反了。共阳极 LED 是**低电平点亮**，所以应该是 `if(pwm_cnt < duty) LED = 0;`。写成 `LED = 1` 就是全亮当"占空比"用（也就是亮的比例反过来了）。

### 3. 灯能呼吸，但能看出明显的闪烁

PWM 频率太低了。检查：

1. 初值算对没有（100 µs 应该是 `0xFFA4`）；
2. `pwm_cnt >= 100` 的阈值是不是被改成了更大的数（比如 200，频率就掉到 50 Hz）；
3. 芯片是不是被设成了 1T 模式（那样节拍会快 12 倍，反而不会闪，但呼吸会快得看不清）。

### 4. 呼吸不平滑，有明显台阶

这是 100 级分辨率的正常表现。想更平滑就把级数加上去（比如 200 级），但要注意：级数翻倍会让周期翻倍，为了保持 100 Hz 就得把节拍缩到 50 µs——又回到了"中断吃满 CPU"的问题。**分辨率和 CPU 占用是一对矛盾**，教学板上 100 级是个平衡点。

### 5. 改了主循环的延时，灯闪了

不可能。真闪了说明你的波形不是定时器产生的，检查是不是还在用第 6 讲那套 `Delay_10us` 循环。

### 6. 蜂鸣器跟着响

`P2.5` 被拉低了。检查是不是哪里写了 `P2 = ...` 整口赋值，或者把呼吸灯改到了 P2.5 上。

### 7. 中断里加了 `Delay_ms`，灯变得乱七八糟

`Delay_ms` 是阻塞的，中断里一旦延时超过一个节拍（100 µs），下一次定时器溢出就只能排队等——波形彻底乱掉。**中断里只能做几句赋值**，这条规则从第 8 讲到第 12 讲一直在强调。

## 从第 10 讲到第 11 讲

| 方面 | 第 10 讲（定时器秒表） | 第 11 讲（定时器 PWM） |
| --- | --- | --- |
| 定时时间 | 10 ms | 100 µs |
| 中断频率 | 100 Hz | 10 kHz |
| 中断里做什么 | 累加计数 | 比较占空比、写引脚 |
| 中断长度要求 | 不高（10 ms 里随便干） | 极严（必须远小于 100 µs） |
| 主循环做什么 | 显示、按键 | 每 10 ms 改一次占空比 |
| 定时器角色 | "闹钟" | "波形发生器" |
| 输出 | 数码管数字 | 亮度（PWM 占空比） |
| 额外派生节拍 | 无 | 500 ms 让 D2 翻转 |

同一套"算初值 + 写中断"的骨架，节拍从 10 ms 缩到 100 µs，用途就从"计时"变成了"生成波形"。**定时器真正的价值不是"定时"，而是"把周期性的事情从主循环手里接过来"**。

## 小结

| 知识点 | 出现在哪里 |
| --- | --- |
| 100 µs 初值计算（92 个机器周期，`0xFFA4`） | 节拍：100 µs |
| 用 0~99 计数器与占空比比较生成 PWM | 占空比：一个 0~99 的计数器 |
| 频率、级数、CPU 占用的三角制约 | 为什么是 100 级 |
| 中断时间预算：不超过节拍的 50% | 中断要多短 |
| 50 µs 节拍为什么撑不住 | 50 µs 为什么不行 |
| 一个定时器派生多个慢节拍 | 一个定时器，两个节拍 |
| 改参数不影响波形（解耦） | 为什么主循环只改参数 |
| `duty` 必须加 `volatile` | `pwm_cnt` 为什么要加 `volatile` |
| `unsigned char` 减到 0 再减会变 255 | 主循环的方向控制 |
| 中断里不能加阻塞延时 | 常见问题 |
