前十一讲，板子一直是自己在玩：按键按它、数码管显示它、灯闪它的。你只能靠"看现象"猜它在想什么，它也没法告诉你"我收到什么了"。

这一讲给它接一条能和电脑说话的线——**串口**。

有了串口，调试方式就变了：以前程序不工作，你只能盯着板子猜；现在可以让板子在关键位置打印一句话，或者把收到的每个字节原样回显给你。**会不会用串口，是"能写程序"和"能调试程序"的分界线。**

**本讲功能**：电脑上的串口助手发命令，板子控制 8 颗 LED，并把结果回给电脑。

| 上位机发送 | 板子现象 | 板子回复 |
| --- | --- | --- |
| `1ON` | LED1 点亮 | `LED1 ON` |
| `1 OFF` | LED1 熄灭 | `LED1 OFF` |
| `ALLON` | 8 颗全亮 | `ALL ON` |
| `ALLOFF` | 8 颗全灭 | `ALL OFF` |
| `9ON`、`abc`、乱码 | 灯不动 | `ERR: 1ON/1OFF/ALLON/ALLOFF` |

命令里的空格可有可无、大小写不敏感——`1ON`、`1 on`、`1 On` 都算数。

## 关于普中 A2

本讲用到的硬件：

| 模块 | 连接方式 | 说明 |
| --- | --- | --- |
| 板载 CH340 | USB 转串口芯片 | 和下载程序共用同一个 USB 口 |
| 单片机 RXD | P3.0 | 接收电脑发来的数据 |
| 单片机 TXD | P3.1 | 把数据发给电脑 |
| LED | P2.0~P2.7，共阳极，低电平点亮 | 被控对象 |
| 蜂鸣器 | 经跳线接 P2.5 | ⚠ `5ON` 会让它响 |
| 按键 K1 / K2 | P3.1 / P3.0 | ⚠ 和串口共用，本讲不能按 |
| 晶振 | 11.0592 MHz | ✅ 这个数字对串口特别重要 |

> ⚠ **K1 和 K2 这一讲不能用。** K1 接 P3.1（TXD）、K2 接 P3.0（RXD），这两个引脚正在被串口占用。按 K1 相当于把发送线拉低，电脑会收到一堆乱码；按 K2 相当于自己给自己发数据。

> ⚠ **LED5 和蜂鸣器共用 P2.5。** 发 `5ON` 的时候蜂鸣器会跟着叫——不是程序错了，是硬件这么连的（第 5 讲讲义里提过）。

## 串口到底在干什么

### 一根线怎么传 8 位

并口传数据是一条线一位：8 位数据要 8 根线，同一时刻全部送达。串口反其道而行：**只用 1 根线，一位一位排队送过去**。

```text
并口（8 根线）：

  D0 ────────────────►
  D1 ────────────────►
  ……                  同一时刻，8 位同时到
  D7 ────────────────►

串口（1 根线）：

  ─────► D0 ─► D1 ─► D2 ─► …… ─► D7 ─────►
         一位一位排队，按时间先后到达
```

代价是要约定好"多快传一位"，好处是一根线就够了，而且线拉得远也没问题。电脑和单片机之间、两块单片机之间、单片机和模块（蓝牙、WiFi、GPS）之间，用的基本都是这个办法。

### 帧格式

一根线上只有 0 和 1，接收方怎么知道"哪一位是第一位"？靠帧格式。

```text
 起始位   D0   D1   D2   D3   D4   D5   D6   D7   停止位
   0      b0   b1   b2   b3   b4   b5   b6   b7     1
 └─────────────────────────────────────────────────────┘
        一帧 = 10 位（本讲用的 8N1 格式）
```

| 部分 | 内容 | 作用 |
| --- | --- | --- |
| 起始位 | 固定为 0 | 从"一直高电平的空闲状态"跳变到低，告诉对方"要开始了" |
| 数据位 | 8 位，**低位先发** | 真正的内容 |
| 停止位 | 固定为 1 | 收尾，让线路回到高电平 |
| 校验位 | 本讲不用 | 检错用的，8N1 里的 N 就是"无校验" |

"8N1"这个说法就是这意思：8 位数据、无校验（None）、1 位停止位。

> ⚠ **数据位是"低位先发"。** 如果你用示波器看，看到的第一位是 D0 不是 D7。写程序时不用管这个，硬件会处理；但调试时对着波形数位，就得按这个顺序数。

### 波特率

波特率就是"每秒传多少位"，单位 bps（bit per second）。

本讲用 **9600**，也就是每位用时：

```text
1 / 9600 ≈ 104 µs
```

一帧 10 位，所以一个字节占 1.04 ms。发一条 10 个字符的回显（比如 `LED3 OFF\r\n`）：

```text
10 个字节 × 1.04 ms ≈ 10.4 ms
```

这个数字后面会反复用到——**它是"串口很慢"的根源**。

> ⚠ **两边的波特率必须完全一致。** 差一点点还能勉强对上，差一倍就全是乱码。串口助手里的 9600 和程序里的 `TH1 = 0xFD` 是一根绳上的两头。

## 11.0592 MHz 为什么是"串口专用"

前面几讲你大概觉得 11.0592 MHz 是个怪数字——为什么不干脆用 12 MHz？

因为 12 MHz 算不出 9600。

波特率由定时器产生，初值必须是整数：

```text
定时器1 溢出率 = 晶振频率 / (12 × (256 - TH1))
波特率 = 溢出率 / 32

反推：256 - TH1 = 晶振频率 / (12 × 32 × 波特率)
```

代入两个晶振试一次：

| 晶振 | `256 - TH1` | 取整后实际波特率 | 误差 |
| --- | --- | --- | --- |
| 12 MHz | 12000000 / (12 × 32 × 9600) = 3.255 | 3 → 9615 | 0.16% ← 单次还行，但累积误差大 |
| 11.0592 MHz | 11059200 / (12 × 32 × 9600) = **3.000** | 3 → 9600 | **0%** |

11.0592 MHz 是 9600 的整数倍：

```text
11059200 = 9600 × 1152
```

不只是 9600，常见波特率它全能整除：

| 波特率 | `256 - TH1` | 实际 |
| --- | --- | --- |
| 1200 | 240 | 1200 |
| 2400 | 120 | 2400 |
| 4800 | 60 | 4800 |
| 9600 | 3 | 9600 |
| 19200（SMOD=1） | 3 | 19200 |
| 115200 | 0.125 | ❌ 算不出整数 |

> ⚠ **这就是开发板上装 11.0592 MHz 而不是 12 MHz 的原因。** 代价是定时器算出来都是小数（10 ms 是 9216 个机器周期而不是 10000），前两讲那种"初值不整"的别扭感，就是为串口让的路。

## 定时器的第三种用法

第 10 讲定时器产生**中断**（计时），第 11 讲定时器产生**波形**（PWM）。这一讲是第三种：

**定时器当分频器，而且完全不进中断。**

### 模式 2 自动重装

模式 2 是"8 位自动重装"：计数器只用 `TL1`，数到 256 溢出时，硬件自动把 `TH1` 的值重新装进 `TL1`，然后继续数。

```text
          TH1 里放着初值（不变）
                  │
                  ▼
    ┌─────── TL1 ───────┐
    │ 0xFD → 0xFE → 0xFF │ ──溢出──► 输出一个脉冲
    └─────────┬──────────┘           │
              ▲                      │
              └──────────────────────┘
                 硬件自动重装 0xFD，不用软件管
```

**关键好处：不用软件重装初值。** 模式 1 每次溢出都得在中断里写两句 `TH0`/`TL0`，一旦晚了几个周期就丢时间；模式 2 硬件自己管，锯齿完全均匀——波特率最怕的就是不均匀。

### 初值 0xFD 是怎么来的

```text
256 - TH1 = 11059200 / (12 × 32 × 9600) = 3
TH1 = 256 - 3 = 253 = 0xFD
```

所以：

```c
TH1 = 0xFD;
TL1 = 0xFD;      // 模式 2 里 TL1 是当前计数值，先给个同样的起点
```

> ⚠ **`TL1` 也要写。** 很多人只写 `TH1`，结果第一次溢出要等 `TL1` 从复位值 0x00 数到 0xFF，第一次通信的时间是错的。虽然往往看不出影响，但养成两边都写的习惯。

### 为什么这个定时器不进中断

定时器 1 在这里只输出一个"溢出脉冲"，这个脉冲直接送给串口的波特率发生器。**整个过程硬件闭环，不需要 CPU 参与**，所以：

```c
TR1 = 1;      // 启动定时器1
              // 但没有 ET1 = 1，没有 interrupt 3
```

对比一下三个定时器用法：

| 讲次 | 定时器 | 用途 | 进不进中断 |
| --- | --- | --- | --- |
| 第 10 讲 | 定时器 0 | 每 10 ms 提醒 CPU | 进（`interrupt 1`） |
| 第 11 讲 | 定时器 0 | 每 100 µs 生成波形 | 进（`interrupt 1`） |
| 第 12 讲 | 定时器 1 | 给串口提供波特率时钟 | **不进** |

> ⚠ **为什么用定时器 1 而不是 0？** 因为定时器 0 的模式 1 是 16 位、适合做长定时；定时器 1 的模式 2 恰好是 8 位自动重装、适合做分频。而且 STC89C52 只有两个定时器，分工刚好。如果两个都要用（又要定时又要串口），就得挑：定时器 1 干串口，定时器 0 干别的。

## 寄存器：SCON 与 TCON

串口的配置集中在两个寄存器里。

**SCON（串口控制寄存器，地址 0x98）**

| 位 | 名称 | 本讲设置 | 含义 |
| --- | --- | --- | --- |
| SM0 SM1 | 工作方式 | `0 1` | 方式 1：8 位 UART，波特率可变 |
| SM2 | 多机通信 | 0 | 方式 1 不用 |
| REN | 允许接收 | **1** | 不写 1 就永远收不到数据 |
| TB8 RB8 | 第 9 位 | 0 | 方式 1 不用 |
| TI | 发送完成标志 | 硬件置 1 | 发完一个字节置 1，**必须软件清 0** |
| RI | 接收完成标志 | 硬件置 1 | 收到一个字节置 1，**必须软件清 0** |

本讲写 `SCON = 0x50`：

```text
0x50 = 0101 0000
       ││││ │││└─ RI  = 0
       ││││ ││└── TI  = 0
       ││││ │└─── RB8 = 0
       ││││ └──── TB8 = 0
       │││└────── REN = 1  ← 允许接收
       │└──────── SM2 = 0
       └───────── SM0 SM1 = 01 → 方式1
```

> ⚠ **`REN` 是新手最容易忘的一位。** 忘了它，板子能发不能收——发回显一切正常，但电脑发什么都像没听见。

**TCON（定时器控制寄存器，地址 0x88）**

这一讲只关心它给串口用的部分：

| 位 | 名称 | 含义 |
| --- | --- | --- |
| TR1 | 定时器 1 运行 | 1 = 启动（波特率时钟开始跑） |
| TR0 | 定时器 0 运行 | 本讲不用 |

注意 `TCON` 里还有 `IT0`/`IT1`（外部中断触发方式）和 `IE0`/`IE1`（外部中断标志），第 8、9 讲用过。**同一个寄存器管着好几件不相干的事**，这是 51 单片机的常态——写的时候用"与或"的方式改某几位，别整字节赋值。

## 接收：用中断

收了字节，程序得知道。两种办法：

| 办法 | 写法 | 缺点 |
| --- | --- | --- |
| 查询 | `while(RI == 0);` 死等 | 等的这段时间什么也干不了 |
| 中断 | `interrupt 4` 里处理 | 稍微复杂一点 |

本讲用中断。理由和第 8、9 讲一样：**等待是主循环的浪费**。上位机可能隔几分钟才发一条命令，主循环不能一直盯着 `RI` 看。

### 中断号 4 的尴尬

`interrupt 4` 是**串口唯一的中断号**，但串口有两个事件：收到一个字节（`RI`）、发完一个字节（`TI`）。它们共用同一个中断入口。

所以 ISR 进来第一件事就是判断"是谁叫我"，并且**两个标志都记得清**：

```c
void Uart_ISR(void) interrupt 4
{
    if(RI == 1) { RI = 0; /* 收数据 */ }
    if(TI == 1) { TI = 0; /* 发完了 */ }
}
```

> ⚠ **两个 `if`，不是 `if...else`。** 有一瞬间 `RI` 和 `TI` 可能同时为 1（一个字节刚收完、另一个刚发完），用 `else` 会漏掉一个，那个标志就会一直挂着，中断反复进入。

> ⚠ **`RI` 必须软件清 0，`TI` 同理。** 硬件只负责置 1，不管清 0。忘了清，中断会一直重入，主循环再也回不去——现象是"程序卡死"。

## 判帧：一条命令到哪算结束

这是本讲最容易出问题的地方。

串口是**字节流**：电脑发 `1ON`，板子收到的是 `'1'`、`'O'`、`'N'` 三个字节，一个接一个。板子怎么知道"这条命令说完了"？

三种常见办法：

| 办法 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 定长 | 收够 N 个字节就处理 | 简单 | 命令长度必须固定 |
| 结束符 | 收到 `\r` 或 `\n` 就处理 | 可靠、通用 | **上位机必须发换行** |
| 空闲判帧 | 一段时间没新字节就处理 | 上位机怎么发都行 | 需要计时，慢一点 |

> ⚠ **本讲把后面两种都做了，这不是为了复杂而复杂。**
>
> 只认 `\r\n` 的话，串口助手里那个"发送新行"没勾，板子就**永远收不到一条完整命令**——现象是发什么都没反应，但发字节是正常的。这个坑调试起来极其难受，因为所有代码看起来都对。
>
> 所以本讲既认 `\r\n`（快），又认"静默 100 ms"（兜底）。

**为什么是 100 ms？**

```text
9600bps 下，连续两个字节的间隔：约 1.04 ms
人在助手里连续点击发送的间隔：几百毫秒到几秒

100 ms 夹在中间：远大于字节间隔（不会误判），
                 远小于人的操作间隔（不会把两条命令粘成一条）
```

代码里是 `CMD_IDLE_MS`，想改直接改这个宏。

> ⚠ **空闲判帧要求主循环一直在跑。** 它靠主循环每 1 ms 调一次 `Uart_CheckIdle()` 来数拍子。如果主循环里塞了个 `Delay_ms(500)`，那"100 ms"就变成了"500 ms"，判帧会变慢。这类"靠主循环数时间"的写法，永远是主循环越长越不准。

## 接收放在中断，解析放在主循环

ISR 只做一件事：把字节塞进缓冲区，然后赶紧返回。解析、控制灯、回显，全在主循环里做。

为什么不干脆在 ISR 里解析完、直接回显？算一笔时间账：

```text
回显一条 "LED3 OFF\r\n" = 10 个字节
10 × 1.04 ms ≈ 10.4 ms
```

如果这 10.4 ms 在 ISR 里度过，会怎样？

```text
ISR 里发送回显（10.4ms）：
┌──────────────────────────────────┐  ← ISR 占着 CPU
│  发 L E D 3   空 O F F \r \n      │
└──────────────────────────────────┘
        ▲
        │ 这期间上位机如果又发来一条命令
        │ 字节会被硬件收进 SBUF，但 RI 没人处理
        │ 下一个字节到来时，上一个字节就被覆盖 → 丢数据
```

**串口接收只有 1 个字节的硬件缓冲（SBUF）**。CPU 在忙别的、没来得及读走，新字节一来就把旧的冲掉了。

所以分工必须是：

| 位置 | 职责 | 时间要求 |
| --- | --- | --- |
| ISR | 读走 SBUF、存进数组、置标志 | 必须在 1 ms 内返回 |
| 主循环 | 解析命令、控制灯、发送回显 | 慢一点没关系 |

这就是"**中断里只做搬运，业务放主循环**"——第 8 讲到第 12 讲一直在讲的同一条规矩。

### 发送时的一个坑：`while(!TI)` 会死等

教科书上常见的发送函数长这样：

```c
SBUF = dat;
while(TI == 0);      // ← 等发完
TI = 0;
```

这段代码在"中断没开"时没问题。但本讲 `ES = 1`，串口中断是开着的——主循环刚把 `TI` 清 0，中断可能恰好在这时进来，**抢先又把 `TI` 清了一遍**。主循环再回去看 `TI`，还是 0，于是永远等下去。

现象：板子上电后回显一条，然后整个卡死。

本讲的办法是用一个自己的标志 `tx_busy`：

```c
void Uart_SendByte(unsigned char dat)
{
    while(tx_busy == 1);     // 上一字节还没发完，等着
    tx_busy = 1;             // 我占了发送权
    SBUF = dat;              // 开始发
}                            // 发完由 ISR 把 tx_busy 清 0
```

`tx_busy` 只有两处会改：主循环置 1、ISR 清 0，职责分明，不会被抢。

> ⚠ **`tx_busy` 必须是 `volatile`。** 它在 ISR 里被改，主循环在等它。不加 `volatile`，编译器可能认为"这个变量在 `while` 里没人改"，把循环优化掉。

## 网页版串口助手怎么用

本讲用网页版串口助手：**<https://serial.keysking.com/#/>**

它靠浏览器的 Web Serial 接口直接访问串口，不用装软件。好处是干净、跨平台；坏处是对浏览器有要求。

### 先关 STC-ISP

**这是最容易卡住的一步。**

```text
  板子 ──── USB ──── 电脑
                     │
                     ├── STC-ISP（下载程序时占用 COM3）
                     └── 串口助手（调试时占用 COM3）

一个串口同一时刻只能被一个程序打开。
```

所以流程必须是：

1. 先用 STC-ISP 下载程序 → **下载完关掉 STC-ISP**（不是最小化，是关掉，或者点"停止"释放串口）；
2. 再打开串口助手，选 COM 口、设波特率、连接；
3. 调试完要改程序 → 关掉串口助手 → 打开 STC-ISP 下载 → 再重复。

> ⚠ **如果串口助手里找不到串口，八成是 STC-ISP 还开着。** 反过来也一样：STC-ISP 提示"找不到串口"，先看串口助手是不是还连着。

### 浏览器要求

| 项目 | 要求 |
| --- | --- |
| 浏览器 | **Chrome 或 Edge**（89 版本以上）。Firefox、Safari 不支持 Web Serial |
| 网址 | 必须是 HTTPS（这个网站是），本地文件或 HTTP 页面不行 |
| 权限 | 第一次连接会弹窗问"是否允许访问串口"，必须点**允许** |

### 设置项

| 项目 | 设置 |
| --- | --- |
| 波特率 | **9600** |
| 数据位 | 8 |
| 校验位 | 无（None） |
| 停止位 | 1 |
| 流控 | 无 |
| 发送新行 | **勾不勾都行**（本讲做了空闲判帧，两种都认） |
| 十六进制显示 | **关掉**（我们要看字符） |

> ⚠ **一定要用半角字符。** 中文输入法下打出来的 `１ＯＮ`（全角）和 `1ON`（半角）是完全不同的字节，板子会回 `ERR`。看到一直回 ERR，先检查输入法。

## 完整代码

`main.c`：

```c
/* 调用头文件 */
#include "reg52.h"
#include "Uart.h"

/* 引脚端口宏定义 */
// 8 个 LED 全接在 P2 口，共阳极，低电平点亮
#define LED P2

/* 变量定义 */
unsigned char cmd_buf[16];		// 存放从接收缓冲区取出来的命令


/**
  * @brief	把字符串里的小写字母全部换成大写
  * @param	str  要处理的字符串（原地修改）
  * @retval	无
  * @note	这样不管上位机发 ON、on 还是 On，板子都能认
*/
void To_Upper(unsigned char *str)
{
	while(*str != '\0')
	{
		if(*str >= 'a' && *str <= 'z')
		{
			*str = *str - 'a' + 'A';		// 小写字母的 ASCII 码比大写大 32
		}
		str++;
	}
}


/**
  * @brief	比较两个字符串是否完全相同
  * @param	a  字符串1
  * @param	b  字符串2
  * @retval	1 = 相同；0 = 不同
*/
unsigned char Str_Equal(unsigned char *a, unsigned char *b)
{
	while(*a == *b)
	{
		if(*a == '\0')			// 比到两个都结束了，说明完全一样
		{
			return 1;
		}
		a++;
		b++;
	}
	return 0;
}


/**
  * @brief	回复上位机："LEDn ON" 或 "LEDn OFF"
  * @param	n   灯的序号 1~8
  * @param	on  1 = 亮，0 = 灭
  * @retval	无
  * @note	用循环拼接而不是 sprintf，省下好几 KB 的程序空间
*/
void Send_LED_Reply(unsigned char n, unsigned char on)
{
	Uart_SendString("LED");
	Uart_SendByte('0' + n);			// 数字 1~8 加上 '0' 就变成字符 '1'~'8'

	if(on == 1)
	{
		Uart_SendString(" ON\r\n");
	}
	else
	{
		Uart_SendString(" OFF\r\n");
	}
}


/**
  * @brief	把字符串里的空格全部删掉
  * @param	str  要处理的字符串（原地修改）
  * @retval	无
  * @note	这样 "ALL ON" 和 "ALLON"、"1 ON" 和 "1ON" 就成了同一个串，
  			后面解析的时候不用再到处跳空格
*/
void Remove_Space(unsigned char *str)
{
	unsigned char *p = str;		// p 负责往后读
	unsigned char *q = str;		// q 负责往前写，只会追平或者落后于 p

	while(*p != '\0')
	{
		if(*p != ' ')				// 遇到空格就跳过，不往 q 那里写
		{
			*q = *p;
			q++;
		}
		p++;
	}

	*q = '\0';					// 新的结尾（字符串可能被缩短了）
}


/**
  * @brief	解析一条命令并执行
  * @param	cmd  命令字符串：单颗灯用 "1ON"、"1OFF"，整排用 "ALL ON"、"ALL OFF"
  * @retval	无
  * @note	命令里有没有空格都行，"1ON" 和 "1 ON"、"ALLON" 和 "ALL ON" 都认；
  			命令不合法时回一条 ERR
*/
void Do_Command(unsigned char *cmd)
{
	unsigned char n;
	unsigned char mask;
	unsigned char *p;

	To_Upper(cmd);			// 先统一转大写，后面就只需要比 "ON" 和 "OFF"
	Remove_Space(cmd);		// 再把空格全删掉，"ALL ON" 就变成了 "ALLON"
	p = cmd;

	// 整排控制：8 颗灯一起开、或者一起关
	if(Str_Equal(p, "ALLON") == 1)
	{
		LED = 0x00;			// 8 位全清 0 → 8 颗灯全亮
		Uart_SendString("ALL ON\r\n");
		return;
	}

	if(Str_Equal(p, "ALLOFF") == 1)
	{
		LED = 0xFF;			// 8 位全置 1 → 8 颗灯全灭
		Uart_SendString("ALL OFF\r\n");
		return;
	}

	// 单颗控制：第 1 个字符必须是 1~8，表示要点第几颗灯
	if(*p < '1' || *p > '8')
	{
		Uart_SendString("ERR: 1ON/1OFF/ALLON/ALLOFF\r\n");
		return;
	}

	n = *p - '0';				// 字符 '3' 减去 '0' 就是数字 3
	mask = 1 << (n - 1);		// 第 n 颗灯对应的那一位：LED1→0x01，LED8→0x80
	p++;

	if(Str_Equal(p, "ON") == 1)
	{
		LED &= (unsigned char)(~mask);	// 这一位清 0 → 输出低电平 → 灯亮
		Send_LED_Reply(n, 1);
	}
	else if(Str_Equal(p, "OFF") == 1)
	{
		LED |= mask;				// 这一位置 1 → 输出高电平 → 灯灭
		Send_LED_Reply(n, 0);
	}
	else
	{
		Uart_SendString("ERR: 1ON/1OFF/ALLON/ALLOFF\r\n");
	}
}


/**
  * @brief	粗略的 1ms 延时
  * @param	无
  * @retval	无
  * @note	只用来给"空闲判帧"数拍子，不要求精确，差个零点几毫秒没关系。
  			用 volatile 是怕编译器觉得这个循环什么都没干，直接优化掉
*/
void Delay_1ms(void)
{
	volatile unsigned char i;

	for(i = 0; i < 110; i++);
}


/**
  * @brief	主函数
  * @param	无
  * @retval	无
  * @note	收字节在中断里做，解析和回显在主循环里做。
  			这一点很重要：如果发送也放在中断里，发一条回显要 9ms 左右，
  			这 9ms 内上位机再发字节就会丢
*/
int main(void)
{
	LED = 0xFF;			// 上电先把 8 颗灯全部熄灭（低电平才点亮，所以写 1 是灭）
	Uart_Init();		// 串口初始化：9600、8 位数据、无校验、1 位停止

	while(1)
	{
		Uart_CheckIdle();					// 数静默时间：勾不勾"发送新行"都能判出命令结束

		if(Uart_GetCommand(cmd_buf) == 1)	// 收到一条完整命令
		{
			Do_Command(cmd_buf);				// 解析 → 控制灯 → 回显
		}

		Delay_1ms();						// 给上面"数拍子"用的，主循环别有长延时
	}
}
```

`Uart.c`：

```c
/* 调用头文件 */
#include "reg52.h"
#include "Uart.h"

/* 宏定义 */
#define RX_BUF_SIZE 16		// 接收缓冲区大小：一条命令最长 15 个字符，再加一个结束符
#define CMD_IDLE_MS 100		// 静默超过这么久（约 100ms）就认为一条命令说完了

/* 变量定义 */
unsigned char rx_buf[RX_BUF_SIZE];		// 接收缓冲区，中断里往里面塞字节
volatile unsigned char rx_len = 0;		// 已经收到了多少个字节
volatile unsigned char cmd_ready = 0;	// 1 表示缓冲区里已经攒够一条完整命令
volatile unsigned char tx_busy = 0;		// 1 表示上一个字节还没发完
volatile unsigned char rx_new = 0;		// 1 表示刚刚又收到了一个新字节（空闲判帧要用）
unsigned char idle_ms = 0;				// 主循环累计"已经有多久没收到新字节了"


/**
  * @brief	串口初始化：9600bps、8 位数据位、无校验、1 位停止位
  * @param	无
  * @retval	无
  * @note	波特率由定时器1 的模式2 产生，这个定时器只负责"分频"，不会产生中断
*/
void Uart_Init(void)
{
	SCON = 0x50;		// 串口方式1（8 位 UART，波特率可变）；REN=1 允许接收
	TMOD &= 0x0F;		// 保留定时器0 的设置，把定时器1 的部分清掉
	TMOD |= 0x20;		// 定时器1 → 模式2（8 位自动重装），专门用来产生波特率
	TH1 = 0xFD;			// 9600bps @ 11.0592MHz：256 - 11059200/(12×32×9600) = 256 - 3 = 0xFD
	TL1 = 0xFD;			// 模式2 里 TL1 是计数器，中断时会自动从 TH1 重装
	PCON &= 0x7F;		// SMOD = 0，波特率不加倍（这一句不写也行，复位后默认就是 0）
	TR1 = 1;			// 启动定时1，波特率时钟开始工作
	ES  = 1;			// 允许串口中断（接收和发送共用 interrupt 4）
	EA  = 1;			// 打开总中断
}


/**
  * @brief	串口中断服务函数：接收字节，或者发送完一个字节
  * @param	无
  * @retval	无
  * @note	接收和发送共用一个中断号 4，所以进来后要自己判断是 RI 还是 TI 触发的
*/
void Uart_ISR(void) interrupt 4
{
	unsigned char dat;

	/* 一、接收：硬件收到一个字节后会把 RI 置 1 */
	if(RI == 1)
	{
		RI = 0;						// 一定要软件清零，否则会一直进中断
		dat = SBUF;					// 把收到的字节读走
		rx_new = 1;					// 告诉主循环：刚刚又来了一个新字节

		if(cmd_ready == 1)			// 上一条命令还没被主循环取走，这个字节先不要了
		{
			/* 丢弃，等主循环把上一条取走再说 */
		}
		else if(dat == '\r' || dat == '\n')	// 收到回车或者换行，说明一条命令结束了
		{
			if(rx_len > 0)					// 连续收到两个换行时，前一个已经处理过，这里跳过
			{
				rx_buf[rx_len] = '\0';		// 补上字符串结束标志
				cmd_ready = 1;				// 告诉主循环：可以取命令了
			}
		}
		else if(rx_len < RX_BUF_SIZE - 1)	// 缓冲区还没满，先存起来
		{
			rx_buf[rx_len] = dat;
			rx_len++;
		}
		else								// 缓冲区满了说明这条命令明显不对，丢掉重来
		{
			rx_len = 0;
		}
	}

	/* 二、发送：硬件把一个字节发完后会把 TI 置 1 */
	if(TI == 1)
	{
		TI = 0;				// 同样必须软件清零
		tx_busy = 0;		// 告诉发送函数：上一个字节发完了，可以发下一个
	}
}


/**
  * @brief	发送一个字节
  * @param	dat  要发送的字节
  * @retval	无
  * @note	写 SBUF 就相当于"开始发送"，发送完成后硬件会进中断把 tx_busy 清 0
*/
void Uart_SendByte(unsigned char dat)
{
	while(tx_busy == 1);		// 上一个字节还没发完，先等着
	tx_busy = 1;				// 标记"现在开始发"，发完由中断清 0
	SBUF = dat;
}


/**
  * @brief	发送一个字符串
  * @param	str  要发送的字符串，必须以 '\0' 结束
  * @retval	无
*/
void Uart_SendString(unsigned char *str)
{
	while(*str != '\0')
	{
		Uart_SendByte(*str);
		str++;
	}
}


/**
  * @brief	取一条完整命令（主循环调用）
  * @param	cmd  取出来的命令会放在这里，调用者要保证空间够大（至少 16 字节）
  * @retval	1 = 取到了一条完整命令；0 = 还没收到
  * @note	拷贝完立刻清空接收缓冲，这样"解析命令"的这段时间里，
  			新来的字节不会和上一条混在一起
*/
unsigned char Uart_GetCommand(unsigned char *cmd)
{
	unsigned char i;

	if(cmd_ready == 0)			// 还没攒够一条完整命令
	{
		return 0;
	}

	ES = 0;							// 拷贝期间先关串口中断，防止新字节插进来把缓冲区搞乱

	for(i = 0; i <= rx_len; i++)		// 连结尾的 '\0' 一起拷过去
	{
		cmd[i] = rx_buf[i];
	}

	rx_len = 0;					// 收完立刻清空，准备接收下一条命令
	cmd_ready = 0;

	ES = 1;							// 拷贝完了，重新允许串口中断

	return 1;
}


/**
  * @brief	空闲判帧：主循环每 1ms 左右调用一次
  * @param	无
  * @retval	无
  * @note	上位机不一定每次都发回车换行，所以不能只靠 '\r' '\n' 判断命令结束。
  			这里的办法是"数静默时间"：只要连续 100ms 没有新字节进来，
  			就当这条命令已经说完了。勾不勾"发送新行"都能用。
  			注意：这个函数靠主循环反复调用来数时间，所以主循环里不能有长延时
*/
void Uart_CheckIdle(void)
{
	if(rx_new == 1)					// 这一拍里有新字节进来，说明还没说完，重新数
	{
		rx_new = 0;
		idle_ms = 0;
		return;
	}

	if(rx_len == 0 || cmd_ready == 1)	// 缓冲区空的，或者已经攒好一条了，不用数
	{
		idle_ms = 0;
		return;
	}

	if(idle_ms < CMD_IDLE_MS)		// 慢慢累加，最多加到 CMD_IDLE_MS 就不再往上涨
	{
		idle_ms++;
	}

	if(idle_ms >= CMD_IDLE_MS)		// 静默够久了，就当这条命令说完了
	{
		ES = 0;						// 关串口中断，防止下面两步被新字节打断
		rx_buf[rx_len] = '\0';		// 补上字符串结束标志
		cmd_ready = 1;				// 通知主循环：可以取命令了
		idle_ms = 0;				// 计数器归零，等下一条命令重新数
		ES = 1;
	}
}
```

## 逐句讲解

### `Uart_Init`：四行决定能不能通

```c
SCON = 0x50;      // 方式1 + 允许接收
TMOD |= 0x20;     // 定时器1 → 模式2
TH1 = 0xFD;       // 9600bps
TR1 = 1;          // 启动波特率时钟
ES = 1; EA = 1;   // 允许串口中断
```

| 语句 | 少了会怎样 |
| --- | --- |
| `SCON = 0x50` | 串口不工作 |
| `REN = 1`（含在 0x50 里） | 能发不能收 |
| `TMOD |= 0x20` | 波特率不对，全是乱码 |
| `TH1 = 0xFD` | 同上 |
| `TR1 = 1` | 波特率时钟不走，收发都没有 |
| `ES = 1` | 收到字节但不会进中断，`cmd_ready` 永远是 0 |
| `EA = 1` | 同上 |

> ⚠ **`TMOD` 用的是 `|=` 不是 `=`。** 第 10、11 讲用定时器 0 时写的是 `TMOD |= 0x01`，这一讲要动定时器 1 的高 4 位。如果这里写 `TMOD = 0x20`，会顺手把定时器 0 的设置清掉——本讲没开定时器 0 所以看不出问题，但你要是把秒表和串口合到一个工程里，定时器 0 就废了。

### `Uart_ISR`：两个 `if`，都别忘了清零

```c
if(RI == 1) { RI = 0; dat = SBUF; ... }
if(TI == 1) { TI = 0; tx_busy = 0; }
```

收字节那一段有四条分支，按优先级排：

| 条件 | 处理 | 为什么 |
| --- | --- | --- |
| `cmd_ready == 1` | 丢弃这个字节 | 上一条主循环还没取走，再收就乱了 |
| `dat == '\r'` 或 `'\n'` | 补 `'\0'`，置 `cmd_ready` | 明确的分帧信号 |
| 缓冲区没满 | 存进去，`rx_len++` | 正常情况 |
| 缓冲区满了 | `rx_len = 0` 重来 | 说明这条数据明显不对 |

> ⚠ **`rx_buf[rx_len] = '\0'` 这句不能省。** 后面 `Str_Equal` 靠 `'\0'` 判断字符串结尾，没这个结束符就会一直往下比，比到数组外面去，行为不可预测。

### `Uart_SendByte`：为什么先等再占

```c
while(tx_busy == 1);   // 先等：上一字节发完没有
tx_busy = 1;           // 再占：现在归我了
SBUF = dat;            // 写 SBUF = 开始发送
```

顺序不能反。如果先 `tx_busy = 1` 再等，就会把自己锁死（等的人就是自己）。

> ⚠ **`SBUF` 是同一个地址的两个寄存器。** 写 `SBUF` 进的是发送寄存器，读 `SBUF` 出的是接收寄存器。所以 `dat = SBUF` 和 `SBUF = dat` 互不干扰，这是 51 的设计。

### `Uart_GetCommand`：临界区保护

```c
if(cmd_ready == 0) return 0;
ES = 0;                 // 关串口中断
for(i = 0; i <= rx_len; i++) cmd[i] = rx_buf[i];
rx_len = 0; cmd_ready = 0;
ES = 1;                 // 开回来
```

为什么中间要关中断？因为拷贝不是一瞬间完成的：

```text
主循环：拷贝 rx_buf[0] … 拷贝 rx_buf[2]
                              ▲
                              │ ISR 抢进来，往 rx_buf[3] 塞了新字节
                              │ 还改了 rx_len
                              ▼
主循环：接着拷 rx_buf[3] ← 拿到的是新数据，命令被污染了
```

关掉 `ES` 让 ISR 在拷贝期间进不来，拷完再开。这段只有几个字节，关的时间极短，丢不了东西。

> ⚠ **这是"临界区"的标准写法：进来先关，出去再开。** 注意所有出口都要开回来——包括中途 `return` 的分支（这里 `return 0` 在关中断之前，所以没问题）。

### `Uart_CheckIdle`：数静默时间

```c
if(rx_new == 1) { rx_new = 0; idle_ms = 0; return; }   // 有新字节，重新数
if(rx_len == 0 || cmd_ready == 1) { idle_ms = 0; return; }  // 没在收，不用数
idle_ms++;
if(idle_ms >= CMD_IDLE_MS) { /* 补齐结束符，置 cmd_ready */ }
```

三个分支对应三种情形：

| 情形 | 处理 |
| --- | --- |
| 刚来了新字节 | 清零，重新数 100 ms |
| 缓冲区空 / 已经攒好一条 | 不用数 |
| 一直在数且数够了 | 认为命令结束 |

> ⚠ **`idle_count` 加到上限就停住（`if(idle_ms < CMD_IDLE_MS)`），不是无脑加。** 无符号数加到 255 再回绕到 0，会让"已经数了 100 ms"这件事变成"刚清零"，判帧永远触发不了。

### `Do_Command`：先规范化，再解析

```c
To_Upper(cmd);      // 全转大写
Remove_Space(cmd);  // 全删空格
```

先做这两步，后面就只需要比 `"ON"`、`"OFF"`、`"ALLON"` 三种形式，不用再写一堆 `if(*p == ' ')`。这叫"**把输入的多样性在入口处收拢成一种**"，是解析字符串的通用套路。

`Remove_Space` 用的是"双指针"：

```text
p：读指针，一直往前走
q：写指针，只在遇到非空格时写

"1 ON" 的处理过程：
  p→1  q→1   写 '1'
  p→空格      跳过
  p→O  q→O   写 'O'
  p→N  q→N   写 'N'
  最后 q 处补 '\0'
```

原地修改，不需要第二个数组，省 RAM。

> ⚠ **`LED &= (unsigned char)(~mask)` 里的强制类型转换不能省。** `~mask` 在 C 里会先把 `mask` 提升成 `int`（16 位），`~0x01` 变成 `0xFFFE`，再和 `LED` 算就会把高字节也搞掉（对 8 位端口通常没事，但编译器会警告）。转回 `unsigned char` 才是想要的结果。

## 实验现象

烧录后：

1. **上电**：8 颗 LED 全灭。数码管可能会乱跳（因为 P2 被当灯用了），正常。
2. **打开串口助手，连接 COM 口（9600）**：如果板子刚好复位，可能收到一两个乱码字符——上电瞬间引脚电平不稳造成的，正常。
3. **发 `1ON`**：LED1 亮，助手收到 `LED1 ON`。
4. **发 `1OFF`**：LED1 灭，收到 `LED1 OFF`。
5. **发 `ALLON`**：8 颗全亮，收到 `ALL ON`。这一下蜂鸣器**会响**（P2.5 被拉低）。
6. **发 `ALLOFF`**：全灭，收到 `ALL OFF`。
7. **发 `3 on`**（小写 + 空格）：LED3 亮，收到 `LED3 ON`——大小写和空格都被容错处理了。
8. **发 `9ON`**：灯不动，收到 `ERR: 1ON/1OFF/ALLON/ALLOFF`。
9. **发 `abc`**：同上。
10. **不勾"发送新行"再发一次 `1ON`**：仍然有效——空闲判帧在兜底（会慢约 0.1 秒）。

> ⚠ **如果发 `1ON` 后 LED 亮了但没有回显**，那说明接收正常、发送有问题，去看 `ES`/`EA` 和 `tx_busy`。**如果灯不亮也没有回显**，说明接收就没通，先查 `REN`、波特率、COM 口占用。

## 常见问题

### 1. 发什么都没反应，一个字节也收不到

按顺序查：

1. **COM 口被 STC-ISP 占着**——最常见。关掉 STC-ISP 再连；
2. 串口助手的波特率是不是 9600；
3. 程序里 `REN` 是不是 1（`SCON = 0x50` 里已经包含）；
4. 板子是不是真的在跑这个程序（重新下载一次，上电看灯有没有按预期动作）；
5. USB 线是不是只能充电的那种（没有数据线芯）——换根线试试。

### 2. 收到全是乱码

波特率不匹配。检查：

1. 晶振是不是 11.0592 MHz（有的板子是 12 MHz，那 `TH1` 要改成 `0xF4` 附近，而且会有误差）；
2. `SMOD`（`PCON` 第 7 位）是不是 0，程序里写了 `PCON &= 0x7F`；
3. 串口助手那边是不是也设成了 9600。

### 3. 板子会回显，但 LED 不动

接收和发送都通了，问题在解析。检查：

1. 发的命令里灯号是不是 1~8（`0ON` 和 `9ON` 都会回 ERR）；
2. 有没有用全角字符；
3. `ON` 后面有没有多余字符（比如 `1ON.`）。

### 4. 只回显了一次，后面再发就没反应了

上一条命令没被主循环取走，`cmd_ready` 一直挂着，新字节全被"丢弃"分支吃掉。检查主循环是不是卡住了——最可能是 `Uart_SendByte` 里的 `while(tx_busy == 1)` 死等（`TI` 中断没开，或者 `tx_busy` 没加 `volatile`）。

### 5. 按住 K1 或 K2 就乱码 / 死机

K1=P3.1 是 TXD、K2=P3.0 是 RXD，和串口共用。**本讲不要按这两个键**，用 K3/K4 或者干脆不按。

### 6. 网页版助手打不开串口 / 找不到设备

1. 浏览器必须是 Chrome 或 Edge（89+）；
2. 第一次连接要在弹窗里点"允许"；
3. 页面必须是 HTTPS（这个网址是）；
4. 换一根 USB 线 / 换一个 USB 口试试；
5. Windows 上如果 CH340 驱动没装好，设备管理器里会显示黄色感叹号。

### 7. `ALLON` 之后想单独关一颗灯，结果全灭了

`ALLON` 是把 `P2` 整个写 0x00，`1OFF` 是把 P2.0 置 1，其他位保持——所以 `ALLON` 后发 `1OFF` 确实只剩 7 颗亮。**这是按位操作的正确行为**，不是 bug。想让"全亮后再单关"符合直觉，就得在 `ALLON` 之后记住状态再逐位算。

### 8. 数码管上显示乱七八糟的东西

正常。本讲把 P2 整口当 LED 用，P2.2~P2.4 是数码管位选，被拉低就会选中某一位。演示时拔掉位选跳线，或者无视它。

## 从第 11 讲到第 12 讲

| 方面 | 第 11 讲（PWM） | 第 12 讲（串口） |
| --- | --- | --- |
| 定时器 | 定时器 0，模式 1 | 定时器 1，模式 2 |
| 定时器用途 | 产生中断、生成波形 | 当分频器，产生波特率 |
| 是否进中断 | 进（10 kHz） | **不进**，硬件闭环 |
| 中断号 | 1 | 4（收发共用） |
| 中断里做什么 | 比较占空比、写引脚 | 读 SBUF、存数组、置标志 |
| 数据方向 | 单片机 → LED | 电脑 ↔ 单片机（双向） |
| 新增概念 | 占空比、时间预算 | 帧格式、波特率、判帧、临界区 |
| 主循环 | 每 10 ms 改一次 duty | 每 1 ms 数一次空闲，收到命令就解析 |

**定时器的三种用法到这里就齐了**：产生中断（第 10 讲）、生成波形（第 11 讲）、当分频器（第 12 讲）。同一个外设，接不同的输出，就是三种完全不同的功能——这是学单片机最该建立的感觉。

**中断的三条规矩**也贯穿始终：

1. 中断里只做搬运，业务放主循环（第 8、11、12 讲都提到）；
2. 中断要短（第 11 讲算过时间账，第 12 讲算过 10.4 ms 的账）；
3. 共享变量要 `volatile`，共享数据要临界区（第 10 讲的 `tenth`、第 12 讲的 `tx_busy` 和 `ES = 0`）。
